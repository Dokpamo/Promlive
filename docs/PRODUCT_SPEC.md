# 로컬 AI 채팅 앱 기획서

## 1. 제품 개요

사용자가 **AI와 함께 스토리와 등장인물을 만들고, 그 설정으로 대화하는 로컬 앱**이다. 직접 창작하거나 애니메이션·만화·영화·소설 등 기존 작품의 세계관을 활용한 2차 창작형 채팅을 즐길 수 있다.

제작 과정에서는 직접 작성, AI 작성, AI 조사, 사용자 수정을 함께 사용할 수 있다. 앱의 템플릿으로 만들거나 직접 코딩한 화면과 동작에 앱의 AI 호출 기능을 연결한다.

지원 대상은 **iOS·Android·Windows·macOS**다. 카드와 대화는 기기에 저장하며, AI 생성과 조사에는 외부 API를 사용한다. 오프라인에서도 저장된 데이터 열기와 직접 편집을 제공한다.

## 2. 기술 구성

| 영역 | 구성 |
|---|---|
| 화면 | React Native + TypeScript |
| 공통 앱 로직 | strict TypeScript |
| 로컬 저장 | SQLite + SQL |
| 운영체제 연결 | DB·보안 저장·통신·사용자 코드 실행용 플랫폼 어댑터 |
| 사용자 코드 실행 | HTML·CSS·JavaScript 기반의 격리된 웹 실행 영역을 기본안으로 구성 |
| 개발 도구 | Node.js, TypeScript, 자동 테스트 |

화면과 기능 코드는 공유하고, 운영체제별 차이는 어댑터와 실행 호스트에서 처리한다. RN·React·Windows/macOS 플랫폼 패키지 및 네이티브 모듈의 호환 버전은 네 플랫폼 빌드로 확인하고 고정한다.

## 3. 제작과 사용 흐름

### AI와 함께 제작

```text
세계관과 등장인물 선택·입력
  → AI에게 작성 또는 조사 요청
  → 편집 가능한 초안 표시
  → 사용자가 확인·수정
  → 카드에 적용·저장
  → 해당 설정으로 채팅
```

직접 작성한 내용과 AI가 만든 내용은 같은 문서와 저장 경로를 사용한다. 사용자는 AI 응답을 기다리는 동안에도 자신의 내용을 편집할 수 있다.

AI 초안에는 기준이 된 카드의 수정 번호를 연결한다. 적용 시 원본이 달라졌다면 충돌을 알리고, 오래된 결과가 최신 사용자 수정을 덮어쓰지 않도록 한다.

AI가 생성한 정보와 실제 자료를 검색한 결과를 구분한다. 조사 결과도 사용자가 검토하고 수정할 수 있다.

### 템플릿과 직접 코딩

| 방식 | 제작 경험 |
|---|---|
| 템플릿 | 앱이 제공하는 입력 화면에서 세계관·등장인물 등을 직접 작성하거나 AI와 함께 편집한다. |
| 직접 코딩 | 자체 화면과 동작을 작성하고 앱이 제공하는 제한된 AI SDK로 생성·취소를 요청한다. |

두 방식은 카드의 식별·저장 체계를 공유한다. 코드 카드의 내부 구성은 템플릿 입력 항목과 독립적으로 유지한다.

## 4. 반응형 화면

같은 기능과 상태를 유지하면서 **실제 창 크기와 글꼴 크기**에 맞춰 배치한다. 좁은 화면은 현재 작업 중심으로, 넓은 화면은 관련 작업 영역을 함께 볼 수 있도록 구성한다. 구체적인 영역 수와 전환 지점은 실제 화면을 기준으로 정한다.

입력 초안과 AI 생성 작업은 레이아웃과 분리해 유지한다. 창 크기 변경이나 영역 전환으로 작성 내용이 사라지거나 AI 요청이 중복 실행되지 않아야 한다.

모바일에서는 터치·가상 키보드·안전 영역을, 데스크톱에서는 키보드·마우스·휠·창 크기 변경을 검증한다. 글꼴 확대, 입력 포커스, 선택·복사도 지원 기준에 포함한다.

채팅 목록은 필요한 항목만 렌더링하고, 스트리밍 중인 메시지 중심으로 화면을 갱신한다. 수신 빈도와 렌더링 빈도는 분리한다.

## 5. 기본 코드 구성

```text
src/
  app/                 초기화와 구현체 연결
  features/
    cards/             카드 데이터, 직접 편집, AI 초안·적용
    chat/              메시지와 생성 상태, 대화 처리
  ports/               AI 호출과 로컬 저장의 공통 계약
  adapters/            SQLite·AI 제공자·운영체제별 구현
  creator-sdk/         사용자 코드와 앱 사이의 요청 규약
  layout/              공통 반응형 배치
```

의존성은 **화면 → 기능 로직 → 데이터 타입·연결 계약** 순서로 둔다. 어댑터는 해당 계약을 구현하고 `app`에서 연결한다.

화면은 데이터 표시와 상호작용을 담당한다. SQL, 제공자별 통신, 인증 처리는 각 어댑터에 모은다. 기능 로직은 UI 프레임워크와 플랫폼 모듈에 직접 의존하지 않도록 작성한다.

공통화는 실제 반복이나 교체 지점에만 적용한다. 한 기능을 여러 계층으로 불필요하게 나누지 않고, 역할이 분명한 파일과 작은 함수로 구성한다.

## 6. 카드와 로컬 데이터

| 데이터 | 기본 구성 |
|---|---|
| 카드 공통 정보 | 식별자, 제목, 카드 형식 버전, 편집 수정 번호 |
| 템플릿 본문 | 템플릿 식별자·버전, 해당 템플릿의 데이터 |
| 코드 본문 | 실행 형식·버전, 사용자 작성 소스 |
| 대화·메시지 | 카드와의 연결, 메시지 순서, 내용, 생성 상태 |

기본 템플릿은 세계관과 등장인물을 중심으로 정의하고 세부 항목은 제작 화면에 맞춰 확정한다. 대화 기록은 카드 본문과 분리해 저장한다.

SQLite를 영구 데이터의 원본으로 사용하고, 화면에는 현재 필요한 데이터만 읽어 둔다. 긴 대화는 구간 단위로 조회한다.

DB 버전, 카드 형식 버전, 템플릿 버전, 사용자 코드 SDK 버전은 각각 관리한다. 편집 수정 번호인 `revision`은 사용자와 AI 사이의 변경 충돌을 확인하는 데 사용한다.

저장 구조 변경에는 데이터 마이그레이션과 기존 데이터 보존 테스트를 포함한다. 마이그레이션 실패 시 원본을 보존한다. SQL 값은 파라미터로 전달하고, 함께 저장되어야 하는 변경은 짧은 트랜잭션으로 처리한다.

## 7. AI 호출과 채팅 처리

제작과 채팅, 사용자 코드의 AI 요청은 공통 호출 계층을 사용한다. 제공자별 요청 형식, 스트림 해석, 완료 신호와 오류 변환은 어댑터에서 처리한다.

| 처리 항목 | 기준 |
|---|---|
| 요청 | 고유 요청 ID로 로컬 중복 전송을 억제하고, 유료 호출의 재시도 여부를 명확히 한다. |
| 응답 | 수신 순서를 유지하고 생성 중·완료·취소·실패를 구분한다. |
| 중단 | 취소를 통신 계층까지 전달하고 연결과 작업 자원을 정리한다. |
| 저장 | 중간 응답은 묶어서 저장하고 완료·취소·실패 시 최종 상태와 부분 결과를 저장한다. |
| 재시작 | 마지막 저장 지점을 기준으로 미완료 작업을 정리한다. |
| 컨텍스트 | 화면 조회 범위와 AI 전송 범위를 분리하고, 제공자 입력 한도와 잘린 기록을 명확히 처리한다. |

제공자의 정상 완료 신호를 기준으로 완료를 판정한다. 연결이 끊겼을 때 받은 부분 응답은 보존하고 오류 상태를 표시한다. 저장 실패를 성공으로 표시하지 않는다.

사용자에게 외부 API로 전송되는 설정과 대화의 범위를 알린다. 실제 통신에서는 스트리밍, 취소, 시간 제한, 네트워크 끊김을 네 플랫폼에서 확인한다.

## 8. 사용자 코드와 인증 정보

사용자 코드는 앱의 신뢰된 실행 영역과 분리한다. 앱의 AI 기능은 SDK를 통해 제공하고, 호출 권한은 호스트가 해당 실행 인스턴스에 연결한다.

| 경계 | 구현 기준 |
|---|---|
| AI 기능 | 생성·취소 요청을 검증하고 동시 호출·요청량·시간 제한을 적용한다. |
| 인증 정보 | API 키는 OS 보안 저장소에서 관리하며 사용자 코드·카드·로그에 노출하지 않는다. |
| 데이터 접근 | 앱 전체 DB·파일·네이티브 기능에 직접 접근하지 못하게 한다. |
| 외부 통신 | 사용자 코드가 사용하는 네트워크·탐색 경로는 허용 범위 안에서 통제한다. |
| 실행 수명 | 실행 종료 시 권한을 회수하고, 무한 루프·과도한 자원 사용에 대응한다. |

웹 실행 영역과 SDK를 실제로 연결할 때 위 경계를 플랫폼별로 검증한다. 사용자 코드의 정확한 권한 범위와 배포 방식은 플랫폼 제약을 확인해 확정한다.

## 9. 개발 품질 기준

TypeScript의 `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`를 적용한다. 외부 입력·AI 응답·저장 데이터는 경계에서 검증하고, 내부에서는 검증된 타입을 사용한다.

기능별 데이터 타입과 처리 흐름을 한곳에서 읽을 수 있도록 구성한다. 이름은 역할을 드러내고, 변경은 관련 기능과 테스트에 집중한다. 공통 규칙의 중복 구현과 불필요한 전체 데이터 재처리를 피한다.

의존성은 필요한 기능, 네 플랫폼 호환성, 빌드·배포 영향을 확인한 뒤 추가한다. 버전과 lockfile을 함께 관리한다. 외부 코드·의존성의 라이선스 중 앱 배포에 영향을 주는 조건과 필요한 고지 사항을 기록한다.

완료 판단에는 타입 검사, 기능 테스트, 데이터 보존 테스트, 해당 플랫폼의 배포용 빌드 결과를 사용한다. 성능은 실제 대화 데이터와 배포용 빌드로 측정하며, 실행한 검증과 미검증 항목을 구분한다.

## 10. 구현 순서

| 단계 | 확인할 결과 |
|---|---|
| 플랫폼 기반 | 네 운영체제에서 화면 실행, DB 저장·재시작, 인증 정보 저장, 실제 AI 스트림·취소가 동작한다. |
| 핵심 사용 흐름 | 템플릿 작성, AI 작성·조사, 초안 수정·적용, 채팅이 하나의 흐름으로 이어진다. |
| 사용자 코드 | 코드 카드 저장, 격리 실행, SDK 연결과 권한·자원 제한이 동작한다. |
| 화면·품질 검증 | 창 크기·입력 방식 변경, 긴 대화, 오류·중단·재시작, 데이터 마이그레이션을 검증한다. |

## 11. 구현 전 확정할 항목

AI·검색 제공자와 API 키·비용 부담 주체, 템플릿의 세부 입력 항목과 화면 구성, 사용자 코드의 허용 권한, OS 최소 버전과 플랫폼별 모듈 조합을 확정한다.

이 문서는 제품과 구현의 기준이며, 각 기능의 완료 여부는 실제 코드와 검증 결과로 관리한다.
