# 본문 가로 제스처

2026-09-30 사용자 결정: 본문을 좌우로 밀면 먼저 알약을 이동한다. 첫/마지막 알약에서 더 밀면 이전/다음 하단 탭으로 이동한다. 상세·편집의 뒤로가기는 왼쪽 가장자리로 제한하지 않는다.

## 이동 규칙

- 왼쪽으로 밀기: 다음 알약, 마지막 알약이면 다음 탭.
- 오른쪽으로 밀기: 이전 알약, 첫 알약이면 이전 탭.
- 알약이 없는 채팅·설정은 바로 이전/다음 탭으로 이동한다.
- 탭 순서는 서재 → 채팅 → 생성 → 설정. 맨 앞·맨 뒤에서 순환하지 않는다.
- 다른 탭으로 들어가면 해당 탭에서 마지막으로 선택했던 알약과 스크롤 위치를 복원한다.
- 알약 줄은 그 자체를 가로 스크롤해서 원하는 알약을 누를 수 있다. 본문 제스처가 이 스크롤을 가로채지 않는다.
- 상세·편집에서는 본문 어디서 시작해도 오른쪽으로 밀면 바로 아래 화면으로 돌아간다. 편집 → 상세 → 서재처럼 실제 열린 경로를 따른다. 왼쪽 밀기는 앞으로가기로 쓰지 않는다.
- 편집 입력칸의 글자 선택·커서 이동은 입력칸이 우선한다. 상세의 메뉴가 열려 있을 때는 메뉴 닫기/시스템 뒤로가기를 먼저 사용한다.

## 손가락과 화면

- 가로 14dp 이동 후 인식한다. 그 전에 세로 10dp를 벗어나면 가로 전환을 포기해 목록 스크롤에 맡긴다. 한 손가락 동작만 처리한다.
- 같은 탭의 알약 이동에서는 제목·버튼·알약 줄·하단 내비게이션을 고정하고 현재 본문과 다음 본문이 나란히 가로로 이동한다. 두 본문 사이에 빈 화면을 넣지 않고 도착 후 페이드인도 하지 않는다. 알약을 직접 누르면 즉시 전환한다.
- 접힌 상단을 유지한 채 알약을 넘길 때 목적지의 상단 높이도 미리 맞춘다. 짧은 목록에는 상단을 다시 아래로 당겨 펼칠 수 있는 최소 스크롤 범위를 확보한다. 분류의 본문 위치는 가능한 한 유지한다.
- 끝 알약에서 다른 하단 탭으로 넘어갈 때는 제목·알약·본문이 함께 움직이며 다음 탭을 미리 보여준다. 하단 내비게이션과 OS 안전 영역은 고정한다.
- 서재·생성의 필터별 목록은 계속 준비되어 있다. 다음 본문을 이미 그려둔 상태로 이동하며, 선택이 바뀔 때도 같은 목록 인스턴스를 유지한다. 목적지의 중복 상단은 숨기고 현재 상단만 표시한다.
- 폭의 28% 이상 이동하거나, 24dp 이상 움직인 후 같은 방향으로 650dp/s 이상 빠르게 놓으면 전환한다. 반대로 되당기며 놓거나 거리가 짧으면 복귀한다.
- 알약·탭 이동은 놓은 뒤 210ms 감속으로 마무리한다. 뒤로가기는 놓은 속도를 이어받는 감쇠 스프링으로 완료·취소하며 목적지를 지나 튀지 않는다. OS의 동작 줄이기를 켜면 마무리 애니메이션을 생략한다.
- 하단 탭과 알약을 직접 누르면 즉시 전환한다. 진행 중인 제스처/애니메이션의 오래된 완료 콜백은 새 선택을 덮어쓰지 않는다.

## 뒤로가기의 페이지 표현

- 상세·편집을 오른쪽으로 밀면 앞 페이지가 둥근 모서리로 잘리며 넘어간다. 반경은 이동 초반 12% 구간에서 0에서 기기 반경으로 이어져 평상시 화면을 가리지 않는다.
- 페이지의 이동·곡률·그림자는 상태 표시줄 배경을 포함한 전체 창에 적용한다. 상세 표지는 시계·배터리 뒤까지 이어지고, 상단 버튼·메뉴와 편집 콘텐츠는 안전 영역을 확보한다. 상단 버튼의 기존 크기·색·정지 위치와 페이지를 따라 움직이는 방식은 유지한다.
- Android 12 이상은 기존 `ScreenCorners` 모듈의 `WindowInsets.getRoundedCorner` 값을 dp로 읽는다. iOS 26 이상은 새 `ScreenCorners.m`에서 실제 창에 맞춘 투명한 UIView에 `containerConcentricRadius`를 적용하고 공개 `effectiveRadiusForCorner:`로 각 반경을 pt로 읽는다. 회전·창 크기 변경 시 다시 계산하며 비공개 API나 기기 이름별 표를 사용하지 않는다. 유효한 0은 각진 모서리이고, 구형 OS·사용할 수 없는 값은 기존 32dp 기본값을 쓴다.
- iOS식 뒤로가기의 느낌에 맞춰 뒤 화면은 원래 크기를 유지한 채 왼쪽에서 따라 나온다. 시작 위치는 화면 폭의 30%만큼 왼쪽이며, 앞 페이지 이동 속도의 30%로 움직여 뒤로가기 완료 시 제자리에 도착한다. 세로 이동·확대·투명도 변화는 없다. 앞 페이지의 이동·모서리와 뒤 화면의 위치를 같은 네이티브 제스처 값으로 계산하며 취소와 방향 전환도 함께 되감긴다.
- 바로 뒤 화면은 제스처가 시작되기 전부터 불투명한 앞 페이지 뒤에 그려둔다. 손가락을 움직인 뒤 JS 콜백으로 화면을 새로 드러내지 않아 빈 프레임이 끼지 않는다. 가려진 화면의 터치와 접근성은 계속 차단한다.
- 뒤 화면 위의 검은 덮개는 진행률에 따라 12%에서 0%로 옅어진다. 콘텐츠 자체는 불투명하게 유지한다. 앞 페이지의 곡률 바깥에만 약한 그림자가 생기고, 완료·취소 시 사라진다. 그림자와 모서리, 명암, 두 화면 이동은 같은 네이티브 값에 연결한다.
- 편집 → 상세 → 서재에서 편집을 넘길 때는 바로 아래 상세만 드러낸다. 더 아래 서재가 틈으로 중복 노출되지 않는다. 직접 누르는 뒤로가기 버튼과 시스템 뒤로가기는 기존 즉시 복귀를 유지한다.
- 카드·편집·새 카드 버튼으로 열 때는 마운트 전에 `prepareOpen()`으로 공유 이동 값을 화면 폭으로 설정한다. 새 화면은 오른쪽 바깥에서 시작해 0으로 들어오고, 뒤 화면은 제자리에서 왼쪽 30%까지 이동하며 명암이 0%에서 12%로 변한다. 모서리·그림자도 뒤로가기와 같은 값을 반대로 따라간다. 전환 레이어에는 고정된 불투명 배경을 두지 않는다.
- 진입·뒤로가기 마무리는 같은 스프링을 사용한다. 진입이 끝나면 이동 값을 정확히 0으로 맞추고 뒤로가기 제스처를 활성화한다. 진입 중 버튼·시스템 뒤로가기는 즉시 취소하며, 취소된 진입의 늦은 완료 콜백은 화면을 다시 움직이지 않는다. OS 동작 줄이기에서는 진입 애니메이션을 생략한다. 앱 재실행 시 저장된 상세·편집 화면은 진입 요청을 만들지 않고 첫 화면부터 즉시 복원한다.
- 버튼·시스템 뒤로가기·스와이프 모두 닫기 전에 해당 전환의 `finish()`로 네이티브 애니메이션을 멈추고 JS/네이티브 이동 값을 화면 폭으로 맞춘다. 그때 뒤 화면 이동과 명암은 이미 0이다. 화면 제거 후 이전 JS 값이 네이티브 뷰에 다시 반영되는 것을 방지한다.
- 서재의 뒤 화면 연결은 상세용·편집용 두 입력을 계속 유지한다. 경로가 바뀔 때 연결 자체를 교체하지 않고 선택 가중치만 바꾸며, 복귀한 화면에서는 둘 다 0이다.

## 구현

- `swipeNavigation.ts`: 알약 우선 이동, 탭 경계, 마지막 선택 복원, 완료/취소 판정.
- `TabPages.tsx`: 준비한 페이지와 인접 화면 배치. 각 화면을 고정된 Animated 그래프에 붙이고 기준 위치만 갱신한다. 그래프를 서로 교체하면 네이티브에서 이전 위치가 남는 문제가 있어 사용하지 않는다.
- `rootSwipeAnimation.ts` / `BodyMotion.tsx` / `ScrollFrame.tsx`: 같은 탭이면 두 본문에만, 다른 탭이면 전체 페이지에 가로 이동을 적용한다. 고정 상단 밖의 투명한 페이지 레이어를 사용해 인접 본문을 가리지 않으며 각 본문은 고정된 네이티브 그래프에 연결한다.
- `SwipeSurface.tsx`: 목록 본문에만 가로 제스처 연결. 기존 세로 헤더 스크롤과 알약 줄은 별도 영역.
- `NativeHorizontalGesture.tsx`: 설치된 Gesture Handler 2.28의 이벤트를 React Native Animated에 직접 연결한다. 손가락 이동을 JS의 매 프레임 상태 변경으로 전달하지 않는다. 추가 애니메이션 패키지는 설치하지 않는다.
- `HorizontalGesture.tsx`: 웹·데스크톱의 PanResponder 구현. 같은 전환 기준을 사용한다.
- `SwipeBack.tsx` / `backTransition.ts` / `useScreenCorners.ts`: 기기 모서리로 앞 페이지를 자르고 바로 뒤 화면을 왼쪽에서 따라오게 한다. 두 레이어가 하나의 이동 값을 공유한다.
- `ScreenMemory.ts`: `library:all` 등의 필터별 스크롤 저장. 예전 탭별 스냅샷은 당시 선택 필터 하나에만 옮긴다.

제스처 어댑터는 Android/iOS에서 네이티브 구현을 고르고, 웹·macOS·Windows에서 기본 구현을 고른다. 아래 전체 흐름은 Android 에뮬레이터에서 검증했다. iOS는 2026-10-01에 아래 범위로 별도 확인했으며 macOS/Windows 실행은 확인하지 않았다.

## 검증 기록

- 최신 애니메이션 수정 후 TypeScript, 관련 3개 파일의 19개 테스트, 웹 빌드 통과. 웹 번들의 기존 대용량 경고는 남아 있다.
- Android에서 서재 전체 → 요즘 한 거 → 방치 중 → 채팅, 생성 전체 → 작업 중 → 완성 → 내 카드 → 외부 카드 → 설정을 실제 본문 스와이프로 확인했다.
- 마지막 탭에서 순환하지 않음, 이전 탭의 필터 복원, 짧은 드래그 취소, 세로 목록 스크롤과 알약 줄 스크롤 유지, 탭 직접 누르기를 확인했다.
- 상세의 왼쪽 밀기 무시·짧은 오른쪽 밀기 취소·충분한 오른쪽 밀기 뒤로가기를 확인했다. 상세 복귀와 앱 강제 종료/재실행 후 서재 카드의 네이티브 좌표가 이전 위치와 정확히 같았다.
- 편집 내용은 오른쪽 밀기로 나간 뒤 다시 열어도 남는다. 검증용으로 덧붙인 문자는 제거했다. 입력칸의 선택 제스처는 `waitFor` 관계로 뒤로가기보다 우선하며, 입력칸을 밀어도 편집 화면이 닫히지 않는 것을 확인했다.
- `continuous-filters.mp4`에서 상단·알약·하단바가 제자리에 있고 두 본문이 빈 프레임 없이 이어진다. 도착 직전과 직후에도 목적지 본문이 유지된다. 상단 영역 `[0,63][1080,378]`, 하단 `[0,2132][1080,2340]`의 전후 좌표가 같다.
- 접힌 상단 `[0,63][1080,63]`도 알약 도착 후 같은 위치를 유지하고, 짧은 목적지 목록에서 아래로 당기면 다시 펼쳐진다.
- 짧은 목적지에서 접힌 상단을 저장한 뒤 프로세스를 종료·재실행해도 같은 좌표를 유지한다. 네이티브 픽셀 반올림으로 저장 범위가 최소값을 조금 넘는 경우도 복원하도록 회귀 테스트에 포함했다. 복원 후 아래로 당겨 다시 펼치는 동작도 확인했다.
- 최신 `parallax-back.mp4`에서 앞 페이지의 곡률과 뒤 화면이 원래 크기를 유지하며 왼쪽에서 따라오는 동작을 확인했다. `parallax-reverse.mp4`에서는 편집 화면을 오른쪽으로 당겼다가 되돌려 취소하는 동작을 확인했다. 편집 → 상세 → 서재 완료, 서재 좌표 복원, 새 프로세스의 런타임 오류 없음도 확인했다. 이전 확대·세로 상승 영상은 현재 동작이 아니다. 검증 파일은 `/tmp/promlive-swipe-qa/`에 있다.

## iOS 기본 전환과 비교 — 2026-10-01

iPhone 17 Pro Compare / iOS 26.5 시뮬레이터에서 Apple 설정 앱과 현재 Promlive를 실행했다. Promlive의 카드 상세 → 서재 스와이프, 설정 앱의 부분 스와이프 복귀와 뒤로가기 버튼 전환을 녹화했다. 이 관찰은 해당 런타임과 화면에 한정하며, UIKit의 내부 상수를 확인한 것은 아니다. 비교 중 앱 UI 코드는 수정하지 않았다.

## 비교 결과 적용 — 2026-10-01

사용자 결정: 상단 버튼은 기존 방식을 유지하고, 나머지 모서리·명암·그림자·완료/취소 움직임을 적용한다. UIKit 내부 전환을 그대로 호출한 것은 아니며, 위 관찰을 바탕으로 앱의 제스처에 맞춘다. 스프링은 강성 500, 감쇠 45, 질량 1, 목적지 초과 금지를 사용한다. 이 값은 UIKit 내부 상수라는 주장이 아니다.

- iPhone 17 Pro / iOS 26.5 실행 로그에서 네 모서리 모두 시스템 반경 **62pt**를 확인했다. 화면 맨 위부터 아래까지 해당 반경과 iOS의 연속 곡선을 사용한다.
- iOS에서 짧은 뒤로가기 취소, 상세 → 서재 완료, 같은 상세 재진입, 편집 → 상세 복귀를 확인했다. 녹화의 중간 프레임에서도 바로 뒤 화면이 보이고 곡률·명암·경계 그림자가 함께 진행한다. 상단 버튼은 앞 페이지를 따라 움직인다.
- Android에서도 취소·상세 복귀·재진입·편집 복귀를 확인했다. 페이지 프레임은 `[0,0][1080,2340]`, 내부 콘텐츠는 기존처럼 `[0,63][1080,2340]`이다. 복귀 후 서재 카드·상단·하단의 좌표는 시작 전과 정확히 같다.
- 관련 4개 파일의 **23개 테스트**를 통과했다. 뒤 화면 명암·취소 시 그림자 제거·안전 영역·재진입 회귀 검증을 포함한다. iOS 시뮬레이터 네이티브 빌드, TypeScript, 웹 빌드도 통과했다. 웹의 기존 큰 번들 경고는 남아 있다. Android 현재 프로세스의 ReactNativeJS/AndroidRuntime 오류 로그는 없다.
- 적용 후 자료: `/tmp/promlive-ios-back-comparison/final-back.mp4`(최종 그림자), `refined-back-fixed.mp4`, `refined-editor-back.mp4`. 초기 `refined-back.mp4`는 검증 중 발견해 수정한 중간 버전이므로 최종 동작의 근거로 사용하지 않는다.

## Android 즉시 뒤로가기 잔상 수정 — 2026-10-01

사용자가 보고한 상태를 직접 캡처했다. 서재 레이어가 30% 왼쪽으로 이동해 오른쪽이 비고, 뒤 화면용 12% 검은 덮개가 남았다. 1080px 화면에서 루트 경계가 `[0,0][756,2340]`, 흰 배경 픽셀이 RGB 225였다. 크래시나 OS 패널이 아니라 앱의 뒤로가기 전환 값이 남는 현상이었다.

초기 연결 유지 수정만으로는 해결되지 않았다. Android에서 **스와이프 복귀 → 같은 상세 재진입 → 상단 뒤로가기 버튼** 순서로 잔상이 다시 발생하는 것을 확인했다. 네이티브 드라이버의 완료 위치가 JS 렌더 값과 어긋난 채 즉시 복귀하면 이전 이동·명암이 재적용될 수 있었다. 모든 닫기 경로에서 `finish()`를 먼저 호출하고 이어서 화면을 제거하도록 수정했다.

수정 후 동일 순서를 네 번 연속 실행해 루트 `[0,0][1080,2340]`과 흰 배경 RGB 255로 돌아오는 것을 확인했다. 짧은 드래그 취소 뒤 시스템 뒤로가기, 편집 → 상세 스와이프 뒤 상세 버튼 복귀도 통과했다. 생성 목록에서 직접 연 편집 화면도 스와이프 복귀 → 재진입 → 상단 버튼 복귀 후 전체 폭과 밝기를 유지했다. 최종 Android 프로세스의 ReactNativeJS/AndroidRuntime 오류 로그는 없다. iOS에서도 스와이프 복귀 후 재진입·버튼 복귀를 확인했다. TypeScript, 관련 3개 파일의 20개 테스트, 웹 빌드 통과. 회귀 검증은 애니메이션 연결의 유지와 화면 제거 전 이동·명암 0, 제거 후 이전 입력의 영향 차단을 확인한다.
