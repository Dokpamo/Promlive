# 상단과 본문의 스크롤 동기화

2026-09-30. 서재·채팅·생성에서 상단 제목·버튼·알약이 본문보다 늦게 따라오는 문제를 수정한다.

## 원인과 구현

기존 구현은 네이티브 목록의 `onScroll`을 자바스크립트에서 받은 뒤 `hidden.setValue(...)`로 별도 상단 레이어를 이동했다. 본문 이동과 상단 이동 사이에 자바스크립트 처리 및 네이티브 호출 왕복이 들어가므로 같은 화면 프레임의 위치가 어긋날 수 있었다.

- 세 목록 모두 `Animated.FlatList`를 사용한다. `Animated.event`가 `contentOffset.y`를 네이티브 Animated 값에 직접 연결한다.
- `scrollHeaderAnimation.ts`가 실제 목록 범위로 좌표를 제한한 뒤, 이동량을 상단 높이 범위에 누적한다. 상단의 `translateY`도 같은 네이티브 그래프에서 계산한다. 드래그·관성 스크롤 중에는 자바스크립트가 시각적 위치를 다시 쓰지 않는다.
- 자바스크립트는 네이티브 입력 값의 관찰 결과로 손을 놓은 뒤의 마무리 위치만 결정한다. React Native의 파생 노드는 네이티브 값 리스너를 직접 구독하지 않으므로, 원본 스크롤 값과 마무리 보정 값을 관찰한다.
- 일반 구간에서는 목록을 가까운 끝으로 이동시켜 본문과 상단이 함께 마무리된다. 하단 끝 근처에서는 별도 보정 값만 애니메이션하여 본문을 되감지 않고 상단을 마무리한다. 새 드래그가 시작되면 진행 중인 마무리를 취소한다.
- 끝부분 탄성은 계속 본문에만 적용한다. 누적 전에 좌표를 유효 범위로 제한하므로 탄성 복귀를 반대 방향 스크롤로 해석하지 않는다. 상단과 하단 탭바는 탄성 레이어 바깥에 있다.
- 검색·분류·너비·상단 높이가 바뀌면 새 그래프와 맨 위 위치로 시작한다. 짧은 목록에서는 상단을 항상 표시한다. 알약의 가로 스크롤과 상단에서 시작하는 세로 드래그도 유지한다.
- Android/iOS는 네이티브 드라이버를 사용한다. 웹에서는 같은 계산 그래프의 자바스크립트 드라이버를 사용한다.

## 검증 방법

- `ui-scroll-header-animation`은 실제 Animated 그래프를 기존 동작 규칙과 비교한다. 즉시 방향 전환, 양끝 탄성 무시, 상단만 마무리한 뒤의 다음 드래그, 목록 길이 변경, 새 분류의 초기화를 확인한다.
- `ui-scroll-header`는 가까운 쪽으로 마무리하는 규칙과 양끝 처리를 확인한다. `ui-shell`과 `ui-boundary`는 화면·검색·편집 동작 및 기존 UI와의 분리를 확인한다.
- Android 36, `emulator-5564`, 1080 × 2340, 개발 빌드에서 같은 서재 드래그를 수정 전후 각각 녹화한다. 첫 알약과 첫 카드 이미지의 세로 이동을 같은 프레임에서 비교한다.
- 별도 녹화에서는 디버거로 자바스크립트를 700ms 동안 의도적으로 점유시켜, 본문이 움직이는 동안 상단이 자바스크립트를 기다리는지 확인한다. 이 진단 코드는 앱 소스에 추가하지 않는다.
- 화면 녹화·비교 JSON·gfxinfo는 `/tmp/promlive-scroll-sync/`에 보관한다. 프레임 간 위치 일치와 전체 렌더링 성능은 다른 지표이며, 개발 빌드·에뮬레이터·녹화 부하의 결과를 실제 기기 FPS로 일반화하지 않는다.

## 검증 결과

일반 드래그와 역방향 마무리를 수정 전후 각 1회, 700ms JS 점유를 넣은 드래그도 각각 1회 녹화했다. 최초 프레임의 알약·이미지 패치를 비교하고, 본문 이동량 10~170px 및 평균 색 오차 8 미만인 프레임만 집계했다. 아래 수치는 전체 목록의 FPS가 아니라 같은 프레임에서 측정한 두 영역의 세로 이동량 차이다.

| 검사 | 비교 프레임 | 평균 차이 | 95백분위 | 최대 차이 |
|---|---:|---:|---:|---:|
| 수정 전 일반 | 60 | 5.35px | 13px | 42px |
| 수정 후 일반 | 61 | 0.02px | 0px | 1px |
| 수정 전 JS 700ms 점유 | 34 | 29.26px | 80px | 91px |
| 수정 후 JS 700ms 점유 | 35 | 0px | 0px | 0px |

- 근거: `/tmp/promlive-scroll-sync/{before,after,before-stall,after-stall}.mp4`와 같은 이름의 `-motion.json`. 측정 스크립트는 `measure-motion.cjs`다. 인코딩·픽셀 반올림 오차가 있으므로 모든 기기에서 정확히 0px라고 일반화하지 않는다.
- 보조 gfxinfo: 일반 검사에서 수정 전 121프레임 중 117개, 수정 후 122프레임 중 108개가 janky로 분류됐다. 중앙값은 61→57ms, 95백분위는 89→93ms다. 녹화 중 에뮬레이터 결과로 전체 FPS 향상을 주장하지 않는다. 원본은 `before-gfxinfo.txt`·`after-gfxinfo.txt`다.
- 서재·채팅의 맨 위 탄성 중 상단·하단 영역은 캡처 픽셀 차이가 0이었다. 근거는 `overscroll.json`이다. 하단의 짧은 역방향 이동 후 본문은 각각 52px·51px 이동한 위치를 유지했고 상단만 마무리됐다.
- 생성에서 상단 숨김·역방향 완전 노출, 짧은 초안 목록의 상단 유지, 가로 알약 스크롤·필터 초기화도 확인했다. 검색 열기·닫기와 상단에서 시작하는 드래그를 확인했다.
- TypeScript, 관련 테스트 18개, 웹 빌드를 통과했다. 검증 완료 후 앱은 라이트 서재의 맨 위로 복귀했다. iOS 실행 검증은 이번 검사에 포함하지 않았다.
