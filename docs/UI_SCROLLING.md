# 상단과 본문의 스크롤 동기화

2026-09-30. 세로 스크롤에서는 서재·채팅·생성의 상단 제목·버튼·알약과 본문을 드래그부터 자동 마무리까지 함께 이동한다. 가로 알약 전환은 `UI_GESTURES.md`의 별도 규칙을 따른다.

## 원인과 구현

기존 구현은 네이티브 목록의 `onScroll`을 자바스크립트에서 받은 뒤 `hidden.setValue(...)`로 별도 상단 레이어를 이동했다. 본문 이동과 상단 이동 사이에 자바스크립트 처리 및 네이티브 호출 왕복이 들어가므로 같은 화면 프레임의 위치가 어긋날 수 있었다.

- 세 목록 모두 `Animated.FlatList`를 사용한다. `Animated.event`가 `contentOffset.y`를 네이티브 Animated 값에 직접 연결한다.
- `scrollHeaderAnimation.ts`가 실제 목록 범위로 좌표를 제한한 뒤, 이동량을 상단 높이 범위에 누적한다. 상단의 `translateY`도 같은 네이티브 그래프에서 계산한다. 드래그·관성 스크롤 중에는 자바스크립트가 시각적 위치를 다시 쓰지 않는다.
- 자바스크립트는 네이티브 입력 값의 관찰 결과로 손을 놓은 뒤의 마무리 위치를 결정하고, 화면을 다시 그릴 때의 그래프 상태를 유지한다. React Native의 파생 노드는 네이티브 값 리스너를 직접 구독하지 않으므로, 원본 스크롤 값과 목록 범위를 관찰한다.
- 목록 끝을 포함한 모든 구간에서 `scrollToOffset`으로 가까운 표시/숨김 상태까지 이동한다. 이 실제 스크롤 거리를 상단도 그대로 따라가므로, 자동으로 접히거나 펼쳐질 때 본문이 함께 움직인다. 상단만 움직이던 `settleOffset`과 별도 타이밍 애니메이션은 제거했다. 새 터치·드래그는 예약된 마무리를 취소한다.
- 끝부분 탄성은 계속 본문에만 적용한다. 누적 전에 좌표를 유효 범위로 제한하므로 탄성 복귀를 반대 방향 스크롤로 해석하지 않는다. 상단과 하단 탭바는 탄성 레이어 바깥에 있다.
- 검색·너비가 바뀌면 새 그래프와 맨 위 위치로 시작한다. 각 분류는 별도 목록으로 준비해 그 분류의 스크롤·상단 상태를 유지한다. 상단 높이는 실제 측정값으로 그래프를 갱신한다. 짧은 목록은 기본적으로 상단을 표시한다. 가로 전환으로 접힌 상단을 전달받으면 그 높이를 유지하고, 다시 펼칠 수 있는 최소 스크롤 범위를 추가한다. 알약의 가로 스크롤과 상단에서 시작하는 세로 드래그도 유지한다.
- 가로 이동 중에는 세로 상단 마무리 예약을 중지한다. 다른 필터의 상단 상태는 아직 보이지 않을 때 맞춰 도착 순간 갑자기 펼쳐지지 않게 한다.
- Android/iOS는 네이티브 드라이버를 사용한다. 웹에서는 같은 계산 그래프의 자바스크립트 드라이버를 사용한다.

## 검증 방법

- `ui-scroll-header-animation`은 실제 Animated 그래프를 동작 규칙과 비교한다. 즉시 방향 전환, 양끝 탄성 무시, 목록 끝에서 상단과 본문이 같은 거리로 마무리됨, 목록 길이 변경, 새 분류의 초기화를 확인한다.
- `ui-scroll-header`는 가까운 쪽으로 마무리하는 규칙과 양끝 처리를 확인한다. `ui-shell`과 `ui-boundary`는 화면·검색·편집 동작 및 기존 UI와의 분리를 확인한다.
- Android 36, `emulator-5564`, 1080 × 2340, 개발 빌드에서 같은 서재 드래그를 수정 전후 각각 녹화한다. 첫 알약과 첫 카드 이미지의 세로 이동을 같은 프레임에서 비교한다.
- 별도 녹화에서는 디버거로 자바스크립트를 700ms 동안 의도적으로 점유시켜, 본문이 움직이는 동안 상단이 자바스크립트를 기다리는지 확인한다. 이 진단 코드는 앱 소스에 추가하지 않는다.
- 화면 녹화·비교 JSON·gfxinfo는 `/tmp/promlive-scroll-sync/`에 보관한다. 프레임 간 위치 일치와 전체 렌더링 성능은 다른 지표이며, 개발 빌드·에뮬레이터·녹화 부하의 결과를 실제 기기 FPS로 일반화하지 않는다.

## 네이티브 스크롤 도입 시점의 검증 결과

일반 드래그와 역방향 마무리를 수정 전후 각 1회, 700ms JS 점유를 넣은 드래그도 각각 1회 녹화했다. 최초 프레임의 알약·이미지 패치를 비교하고, 본문 이동량 10~170px 및 평균 색 오차 8 미만인 프레임만 집계했다. 아래 수치는 전체 목록의 FPS가 아니라 같은 프레임에서 측정한 두 영역의 세로 이동량 차이다.

| 검사 | 비교 프레임 | 평균 차이 | 95백분위 | 최대 차이 |
|---|---:|---:|---:|---:|
| 수정 전 일반 | 60 | 5.35px | 13px | 42px |
| 수정 후 일반 | 61 | 0.02px | 0px | 1px |
| 수정 전 JS 700ms 점유 | 34 | 29.26px | 80px | 91px |
| 수정 후 JS 700ms 점유 | 35 | 0px | 0px | 0px |

- 근거: `/tmp/promlive-scroll-sync/{before,after,before-stall,after-stall}.mp4`와 같은 이름의 `-motion.json`. 측정 스크립트는 `measure-motion.cjs`다. 인코딩·픽셀 반올림 오차가 있으므로 모든 기기에서 정확히 0px라고 일반화하지 않는다.
- 보조 gfxinfo: 일반 검사에서 수정 전 121프레임 중 117개, 수정 후 122프레임 중 108개가 janky로 분류됐다. 중앙값은 61→57ms, 95백분위는 89→93ms다. 녹화 중 에뮬레이터 결과로 전체 FPS 향상을 주장하지 않는다. 원본은 `before-gfxinfo.txt`·`after-gfxinfo.txt`다.
- 서재·채팅의 맨 위 탄성 중 상단·하단 영역은 캡처 픽셀 차이가 0이었다. 근거는 `overscroll.json`이다. 당시 하단의 짧은 역방향 이동 후 본문은 각각 52px·51px 이동한 위치를 유지했다. 이때 사용한 상단 단독 마무리는 이후 아래의 공동 마무리 동작으로 교체했다.
- 생성에서 상단 숨김·역방향 완전 노출, 짧은 초안 목록의 상단 유지, 가로 알약 스크롤·필터 초기화도 확인했다. 검색 열기·닫기와 상단에서 시작하는 드래그를 확인했다.
- TypeScript, 관련 테스트 18개, 웹 빌드를 통과했다. 검증 완료 후 앱은 라이트 서재의 맨 위로 복귀했다. iOS 실행 검증은 이번 검사에 포함하지 않았다.

## 손을 놓을 때 펼쳐졌다가 접히는 현상

위의 드래그 동기화 검사와 별개로, 한 번의 터치 안에서 방향을 바꾼 뒤 놓을 때 깜빡임이 재현됐다. 수정 전 상태는 `7bc7ac2`에 커밋했다.

- 재현: 상단이 접힌 상태에서 손을 떼지 않고 목록을 내려 상단을 완전히 펼친 다음, 반대로 움직여 절반 이상 접힌 위치에서 놓는다.
- 원인: 네이티브 `diffClamp`는 전체 이동 경로를 누적하지만, 자바스크립트의 같은 노드는 화면을 다시 그릴 때만 계산되고 있었다. 끝에서 잘린 이동량과 중간 방향 전환을 놓치므로 두 위치가 달라졌다. React Native 0.81의 Fabric은 스크롤 종료 시 자바스크립트 그래프를 다시 읽는다. 이때 실제 숨김 거리 약 110.48dp를 0dp로 읽어 완전히 펼친 화면을 잠깐 덮어썼고, 다음 네이티브 마무리 프레임에서 다시 접혔다.
- 수정: `observeInputs`가 스크롤·목록 범위의 각 입력을 받을 때 자바스크립트 그래프도 평가해 누적 상태를 유지한다. 시각적 이동은 계속 네이티브 그래프가 담당한다. 자바스크립트에서 `setValue`로 상단 위치를 다시 쓰지 않는다.
- 호환성: 파생 그래프를 평가하는 공개 동기 API가 없어 `__getValue` 접근을 이 관찰 함수 한 곳에 한정했다. React Native 버전을 올릴 때 입력 관찰 테스트와 네이티브 왕복 드래그를 다시 확인해야 한다.
- 회귀 테스트는 중간에 출력 그래프를 읽지 않고 네이티브 입력 콜백만 전달한다. 한 번의 터치 중 방향 전환, 목록 범위 변경, 구독 해제를 검증한다. 기존처럼 매 입력 직후 출력 값을 검사하는 테스트만으로는 이 문제를 잡을 수 없었다.

Android 36 에뮬레이터의 동일한 왕복 제스처를 녹화했다. 수정 전 `reverse-before.mp4`의 약 2.279초에서 상단이 완전히 펼쳐졌다가 약 2.402초에 다시 접힌 위치로 돌아간다. 수정 후 `reverse-after.mp4`에서는 접히는 구간에 이 재등장이 없다. 원본·진단 기록·프레임별 비교는 `/tmp/promlive-header-flicker/`에 있으며, 진단용 앱 코드는 제거했다. TypeScript, 관련 테스트 20개, 웹 빌드를 통과했다.

채팅·생성에서도 왕복 후 접힘과 역방향 노출, 검색 열기·닫기를 확인했다. 서재에서는 같은 제스처 도중 디버거로 자바스크립트를 800ms 점유시킨 녹화에서도 종료 시 상단의 재등장이 없었다. 근거는 같은 폴더의 `{chats,create,library}-verify.mp4`다. 검증 후 앱을 라이트 서재의 맨 위로 복귀했다. iOS 실기기·시뮬레이터는 이번 검사에 포함하지 않았다.

## 자동 마무리에서 본문도 함께 이동

사용자 요청에 따라 목록 끝에서도 상단만 빠져나가는 처리를 제거했다. 가까운 끝까지 남은 숨김 거리만큼 실제 목록을 스크롤한다. 예를 들어 높이 120인 상단이 100만큼 숨겨진 상태라면 목록과 상단이 모두 20만큼 더 올라간다. 반대로 40만큼 숨겨져 있으면 목록과 상단이 모두 40만큼 내려와 완전히 열린다. 하단 탭바는 이 이동에 포함하지 않는다.

스크롤과 별개로 상단 위치를 보정하지 않으므로, 같은 목록 범위에서는 끝에 도달했을 때 상단도 완전히 숨겨진다. 단위 테스트는 목록 끝의 짧은/긴 역방향 이동과 반복 마무리에서 이 관계를 확인한다. TypeScript, 관련 테스트 21개, 웹 빌드를 통과했다. Android 검증 자료는 `/tmp/promlive-scroll-together/`에 저장한다.

Android에서 손을 놓기 직전과 자동 마무리 후의 UI 좌표를 비교했다. 접힘/펼침 이동량은 서재 −74/+86px, 채팅 −37/+46px, 생성 −72/+86px였고, 여섯 경우 모두 상단과 본문의 이동량 차이는 0px였다. 하단 탭바 위치도 그대로였다. `results.json`, 전후 캡처, 서재 자동 접힘 녹화 `library-close.mp4`가 근거다. 검증 후 앱은 서재 맨 위로 복귀했다.
