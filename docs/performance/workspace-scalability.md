# 대용량 카드·채팅 저장 및 화면 검증

측정일: 2026-10-04. 장기기억, 요약, 검색 증강, AI 요청 생성은 이번 변경 범위에서 제외했다. 이 문서의 결과는 **로컬 저장·화면 표시·스크롤**에 대한 결과다.

이 문서는 먼저 실행한 **10,000자 고정 길이 데이터의 기준 결과**다. 이후 macOS·iOS·Android의 가변 길이 검증에서 스크롤 처리와 기본값을 추가 조정했다. 현재 값은 아래 표에 반영했으며, 최신 원인 분석·네이티브 수치는 [가변 길이 검증 보고서](variable-message-matrix.md)를 따른다.

## 데이터

`scripts/performance/fixture.ts`의 반복문으로 생성했다. 외부 API, 사용자 대화, 언어 모델을 사용하지 않았다.

| 항목 | 실제 생성량 |
| --- | ---: |
| 카드 | 10,000개, 각 인트로 10,000자 |
| 채팅방 | 10,000개 |
| 주 측정 방 | 10,000턴 = 사용자 10,000개 + AI 10,000개 |
| 주 측정 방의 메시지 | 각각 정확히 10,000자, 총 200,000,000자 |
| 나머지 방 | 각각 사용자·AI 메시지 1개씩, 각각 10,000자 |
| 전체 메시지 | 39,998개, 총 399,980,000자 |
| SQLite 파일 | 1,392,840,704바이트 |

SQL 집계로 메시지 수 및 최소·최대 길이가 일치하는지 확인했다. 문자는 한글 BMP 문자이므로 이번 데이터에서는 코드포인트 수와 JavaScript 문자열 길이가 같다. Android는 `com.storyloom.benchmark`, 웹은 `promlive-isolated-performance`라는 별도 저장소를 사용했다. 기존 앱 데이터와 API 키는 수정하지 않았다.

## 적용한 구조

- 기존의 큰 화면 JSON은 처음 한 번만 읽어 행 단위 저장소로 옮긴다. 완료 표시와 데이터는 같은 트랜잭션으로 저장하며 원본은 남긴다. 이후 시작·입력·전송에서는 전체 기록을 다시 읽거나 직렬화하지 않는다.
- Android·iOS·macOS는 SQLite, 웹은 IndexedDB, Windows는 기존 SQLite 연결에 이름이 분리된 테이블을 사용한다.
- 목록은 제목·썸네일 참조·짧은 미리보기만 읽는다. 카드 소개와 갤러리 등 전체 문서는 해당 카드를 열 때 읽는다. `(정렬값, ID)` 커서로 같은 시각의 행도 빠짐없이 이어 읽는다.
- 채팅은 메시지 순번과 글자 수를 먼저 읽어 필요한 본문만 가져온다. 화면에서 멀어진 본문은 메모리에서 비우고, 다시 접근하면 저장소에서 읽는다. 저장된 원문을 삭제하거나 잘라내지 않는다.
- 긴 대화의 복원 위치는 전체 높이가 아니라 메시지 ID·순번·메시지 안의 상대 위치로 기억한다. 앞쪽 추가 로딩과 메모리 정리 시 보던 위치를 유지한다.
- 목록과 대부분의 플랫폼 채팅은 가상 목록으로 표시한다. 최신 iOS 채팅은 저장소가 제한한 작은 범위의 실제 뷰를 유지한다. PC에서 행 높이가 같을 때 위치 변경 통지가 빠지는 문제, 재시작 시 아직 측정하지 않은 목록 높이에 복원 위치가 잘리는 문제도 수정했다.
- 초안 저장은 변경된 방만, 전송은 새 메시지 추가와 초안 비우기를 한 트랜잭션으로 처리한다. 저장 도중 추가 입력·연속 전송, 다른 창의 변경, 실패 후 재시도를 회귀 검사했다.
- 첫 화면용 캐시는 제한된 목록과 선택한 문서 일부만 보관한다. 데이터의 원본은 DB다. 캐시 실패가 저장된 대화를 지우지 않는다.
- 기본 이미지의 큰 base64 문자열을 각 이미지 셀에서 반복 처리하지 않도록 플랫폼별 파일 소스로 바꿨다.

## 기본값과 선택 이유

| 설정 | 값 |
| --- | ---: |
| 목록 한 번 읽기 | 24개 |
| 채팅 한 번 읽기 | 최대 16개, 총 16,000자 예산 |
| 채팅 본문 유지 | 64,000자 / 160개 예산, iOS는 96개 |
| 채팅 미리 읽기 시작 | 끝까지 약 2화면 남았을 때 |
| 채팅 렌더 범위 | Android 3화면, PC 5화면, 배치당 4개; iOS는 위의 제한된 범위 유지 |
| 첫 화면 캐시 | 최대 120,000자 |
| 초안 저장 지연 | 250ms, 전송·앱 상태 변경 시 flush |

10,000자 메시지에서는 추가 읽기당 보통 1개, 정리 후 최대 6개/60,000자가 유지됐다. **화면에 실제로 보이는 메시지나 메시지 하나가 예산보다 큰 경우는 표시를 보존하는 예외**가 있다. 예산을 맞추려고 원문을 자르지 않는다. 목록의 방문한 범위에는 가벼운 메타데이터가 남으며, 전체 앱 메모리가 반드시 64,000자에 해당하는 크기로 고정된다는 뜻은 아니다.

동일한 Android 카드 화면에서 40회 빠른 스와이프를 비교했다.

| 목록 페이지 | 실행 전체에서 읽은 행 | 스크롤 중 조회 횟수 | 스크롤 중 읽은 행 | OS 마감 초과 |
| --- | ---: | ---: | ---: | ---: |
| 12개 | 468 | 32 | 384 | 2 / 621 |
| **24개** | **528** | **16** | **384** | **2 / 621** |
| 48개 | 672 | 8 | 384 | 2 / 618 |

전체 읽기에는 준비된 인접 필터가 포함된다. 24개는 12개보다 초기 데이터가 조금 많지만 스크롤 중 조회를 절반으로 줄였다. 48개보다 초기 읽기량은 적다. 따라서 **이번 데이터와 시험 환경에서의 균형값**으로 선택했다. 모든 기기에서의 수학적 최적값이라고 보장하지 않는다.

## 측정 결과

Android 16 에뮬레이터, 1080×2340, 60Hz, 릴리스 JS 번들로 측정했다. 녹화를 하면서 UI 트리에서 얻은 본문 좌표에 보통 속도와 빠른 스와이프를 보냈다. 빠른 스와이프는 110ms 이동, 80ms 간격이다. 장시간 비교 중 호스트 절전으로 끊긴 실행은 제외했다.

| 대표 녹화 | 전체 영상 프레임 | 본문 전체가 빈 프레임 | OS 프레임 마감 초과 |
| --- | ---: | ---: | ---: |
| 대화 중간에서 140회 빠른 스와이프 | 2,010 | 0 | 2 / 1,992 (0.10%) |
| 대화 중간에서 90회 빠른 스와이프 | 1,326 | 0 | 3 / 1,310 (0.23%) |

| 최종 설정, 대화 75회 빠른 스와이프 | 1,115 | 0 | 2 / 1,098 (0.18%) |

영상의 모든 프레임을 디코딩해서 본문 영역의 밝기·변화량·표시 시각을 분석했고, 일부를 연속 이미지로 직접 확인했다. 녹화 시작 후 첫 스와이프까지의 정지 구간은 움직임 끊김으로 세지 않았다. 위 빠른 스크롤 영상에서 이 시작 구간을 제외한 움직이는 프레임 사이에 34ms 초과 간격은 없었다. 보통 속도 영상에는 149번 프레임에서 **61.345ms 간격 1건**이 있었고 바로 다음 간격은 3.844ms였다. 주변 5개 프레임의 본문이 이어지는 것을 직접 확인했지만, 이 기록만으로 인코딩 시각 지연과 실제 표시 지연을 구분할 수는 없다. 해당 기록도 제외하지 않고 보관했다. 이는 **빈 화면 없이 표시가 이어졌다는 관측**이지, 모든 종류의 지연이 전혀 없다는 증명은 아니다. 에뮬레이터에서도 소수의 OS 마감 초과는 남았다.

대화 90회 실행에서 프로세스 PSS는 약 185MiB, 본문은 최대 60,000자였다. 2억 자 전체를 앱 메모리에 올리지 않고 해당 위치 주변만 유지했다. 같은 실행의 추가 본문 조회는 5회, 각 10,000자였고 측정된 가장 긴 조회는 약 8.0ms였다.

PC 웹(1280×900)에서는 12초 빠른 스크롤을 별도로 검사했다. 화면 갱신 주기는 약 120Hz였다.

| 항목 | 관측 rAF 수 | p95 간격 | 최대 간격 | 34ms 초과 |
| --- | ---: | ---: | ---: | ---: |
| 카드, 최종 24개 단위 | 1,420 | 10.1ms | 24.7ms | 0 |
| 긴 채팅 | 1,438 | 9.8ms | 10.4ms | 0 |

채팅은 위 실행 중 6회/각 10,000자를 읽었으며 최대 60,000자를 유지했다. 추가로 긴 입력·전송 후 재시작 보존, 카드 검색, 깊은 목록 위치 복원을 검사했다. 목록은 저장된 약 33,535px 위치에서 재시작 후 약 33,536px로 복원됐다(레이아웃 반올림 차이).

### 지표 해석과 한계

`dumpsys gfxinfo`의 `Janky frames`와 `Janky frames (legacy)`는 서로 다른 지표다. 대표 채팅 실행의 legacy 값은 97~99%로 높았으므로 이를 숨기거나 두 수치를 같은 의미로 해석하지 않았다. legacy는 고정 주기 기준, 새 지표는 실제 프레임 마감 기준을 반영한다. 렌더 파이프라인과 에뮬레이터 GPU의 영향도 있어 영상 표시 간격과 함께 판단했다. [Android JankTracker 구현](https://android.googlesource.com/platform/frameworks/base/%2B/79cb3c528880/libs/hwui/JankTracker.cpp), [Perfetto FrameTimeline 설명](https://github.com/google/perfetto/blob/main/docs/data-sources/frametimeline.md).

이 문서의 PC 수치는 브라우저 rAF 관측이며 GPU 표시 완료나 macOS 네이티브 프레임을 직접 측정한 값은 아니다. **실제 iPhone·Android 기기·Windows 네이티브 성능은 미측정이다.** 이후 macOS 네이티브와 iOS Simulator에서 측정한 결과는 별도 보고서에 기록했다. 저장소·UI 변경은 공통 경로에 적용했지만 미측정 환경에서 프레임 무결함을 보장하지 않는다. 검색은 정규화된 목록 메타데이터를 훑는 방식으로, 수십만 개 규모나 전문 검색은 별도 인덱스 설계가 필요할 수 있다. 최초 기존 JSON 마이그레이션도 한 번은 원본 읽기 비용이 든다.

## 재현

현재 실행 명령은 [벤치마크 README](../../scripts/performance/README.md)를 따른다. 고정 길이 데이터를 만들려면 생성 명령에서 `--matrix`를 생략한다. 최신 벤치마크 진입점은 별도의 `promlive-performance-matrix` DB를 사용하므로 예전 파일명에 복사하지 않는다. 웹 시안은 다음과 같이 실행한다.

```sh
npx vite build --config scripts/performance/web/vite.config.ts
npx vite preview --config scripts/performance/web/vite.config.ts --host 127.0.0.1
```

`http://127.0.0.1:8786/`에서 더미 데이터 준비 → 카드/채팅 목록/1만 턴 채팅 → 12초 빠른 스크롤을 누른다. 측정 결과에는 조회 수·크기·프레임 간격·본문 보관량이 표시된다. 처음 한 번 IndexedDB에 데이터를 생성하며 실제 앱 저장소와 분리되어 있다.

이 기준 실행 당시 `npm run verify`는 92개 파일/786개 테스트와 웹 빌드를 통과했다. 이후 변경까지 포함한 최종 검증은 **94개 파일/796개 테스트**와 웹 빌드, macOS·iOS·Android 일반 Release 빌드가 통과했다. SQLite와 IndexedDB 양쪽에서 마이그레이션·충돌·중복 전송·검색·페이지 경계·저장 실패를 검사했다. Android 키보드 열기·입력·전송·앱 재시작 후 메시지 보존도 확인했다. 이 추가 기능 확인에서 넣은 메시지는 기준 데이터 집계 및 스크롤 측정 이후에 추가했다.
