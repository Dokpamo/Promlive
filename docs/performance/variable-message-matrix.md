# 메시지 길이가 다른 1만 턴 채팅: 네이티브 검증

측정일: 2026-10-04. [이전 고정 길이 검증](workspace-scalability.md)에 이어, 짧은 메시지가 많이 쌓이는 경우와 긴 메시지가 섞이는 경우를 검사했다. 장기기억과 AI 요청은 범위에 포함하지 않았다. 더미 텍스트는 반복문과 고정 시드로 만들었다.

**이번 비교에서 선택한 기본값은 한 번에 최대 16개·16,000자, 본문 보관 64,000자, 미리 읽기 2화면이다.** iOS에서는 별도의 가상 목록이 스크롤 기준 행을 없애는 문제를 확인해, 읽어온 작은 범위만 실제 뷰로 유지하도록 바꾸고 메시지 수 예산을 96개로 낮췄다. 다른 플랫폼은 160개 예산과 가상 목록을 사용한다. 모든 기기에서의 수학적 최적값이나 무지연을 보장하는 수치는 아니다.

macOS 네이티브와 iOS·Android 에뮬레이터에서 측정했다. **Windows 실행 환경과 실제 휴대폰은 없어서 해당 환경의 성능은 미검증이다.** Windows에는 공통 수정과 격리된 벤치마크 실행 경로를 준비했으며, 네이티브 빌드·측정 성공으로 표기하지 않았다.

## 데이터와 환경

카드 10,000개(각 인트로 10,000자), 채팅방 10,000개를 만들었다. 다음 다섯 방은 각각 사용자 10,000개 + AI 10,000개, 즉 10,000턴이다.

| 방 | 메시지 길이 | 전체 글자 수 |
| --- | --- | ---: |
| `perf-00000` | 모두 10,000자 | 200,000,000 |
| `perf-00001` | 2~49자 | 503,676 |
| `perf-00002` | 모두 1,000자 | 20,000,000 |
| `perf-00003` | 사용자 100~1,000자, AI 1,000~10,000자 | 60,480,434 |
| `perf-00004` | 20~200자 사이에 50,000자 메시지 반복 삽입 | 29,139,626 |

나머지 방에는 짧은 메시지 2개씩을 넣었다. 합계 119,990개 메시지, 310,853,371자다. DB는 1,235,222,528바이트이며 생성 시간은 8.567초였다. 글자 수는 저장할 때의 JavaScript `text.length`(UTF-16 단위)다. 이 더미 한글 본문에서는 코드포인트 수와 같지만, 이모지의 화면상 글자 수와 항상 같은 의미는 아니다. 토큰 수도 아니다.

| 환경 | 조건 |
| --- | --- |
| 호스트 | Apple M4, 메모리 16GB, macOS 26.6.2 |
| Mac 앱 | 네이티브 Release, 1280×752 창, 실제 휠 입력과 자동 스크롤 별도 실행 |
| iOS | iPhone 17 Pro Simulator, iOS 26.5, Release |
| Android | API 36 arm64 에뮬레이터, 1080×2340, 60Hz, Release |
| Windows | 격리 빌드 설정·실행 스크립트만 준비, 실행하지 못함 |

각 네이티브 앱은 별도 벤치마크 식별자와 DB를 사용했다. Mac은 번들 ID만 바꾸면 비샌드박스 DB 경로가 같을 수 있어 DB 파일명도 분리했다. 실제 앱의 카드·대화·API 키에 더미를 섞지 않았다.

## 선택한 설정

| 설정 | 값 | 이유 |
| --- | --- | --- |
| 목록 한 번 읽기 | 24개 | 앞선 12/24/48 비교에서 초기 읽기와 조회 횟수의 절충 |
| 메시지 한 번 읽기 | 최대 16개, 총 16,000자 예산 | 짧은 문장은 수로, 긴 문장은 크기로 제한 |
| 본문 보관 | 64,000자와 160개 예산 | 대화 전체 길이와 무관하게 근처 본문만 유지 |
| iOS 본문 보관 | 64,000자와 96개 예산 | 읽은 범위를 실제 뷰로 유지하므로 개수 예산을 더 작게 설정 |
| 미리 읽기 | 읽은 범위 끝까지 약 2화면 남았을 때 | 도착 후 조회를 시작하는 대기 감소 |
| Mac·Windows 가상 렌더 범위 | 총 5화면, 배치 4개 | Mac의 작은 렌더 범위에서 나타난 부분 공백을 줄임; Windows 실측은 남음 |
| Android 가상 렌더 범위 | 총 3화면, 배치 4개 | 이번 네이티브 스와이프에서 정상 조회 시 경계 대기 없음 |
| iOS 렌더 | 저장소가 제한한 범위만 유지 | 가상 빈 공간으로 기준 행이 교체되는 문제 방지 |
| 첫 화면 캐시 | 120,000자, 목록 캐시 4개 | 빠른 재진입과 캐시 크기 제한 |

16개와 16,000자는 둘 중 먼저 도달하는 쪽을 따른다. 예를 들어 1,000자 메시지는 16개, 10,000자 메시지는 보통 1개를 읽는다. 50,000자처럼 예산보다 큰 메시지 하나는 원문 그대로 읽는다. 대화 중간 복원은 기준 메시지 앞뒤 페이지가 필요해 초기 조회가 두 번일 수 있다.

64,000자·96/160개는 정리 후 목표 예산이다. 병합 직후에는 새 페이지가 잠깐 더해지며, 화면에 보이는 메시지는 정리 예외로 보호한다. iOS 짧은 대화에서 실제 최대치는 112개(96+16), 3,080자였다. 이것이 전체 앱 메모리를 64KB로 제한한다는 뜻은 아니다. 이미지를 포함한 네이티브 뷰·엔진 메모리는 별도다.

## 찾아서 수정한 원인

### DB를 읽으며 본문 글자 수를 다시 세지 않는다

메시지 저장 시 기록한 `characters`를 순번과 함께 읽고, 선택한 본문만 가져온다. `(chat_id, sequence, characters)` 인덱스를 추가해 길이 확인 때문에 큰 본문이 들어 있는 테이블 페이지까지 방문하는 비용을 줄였다.

같은 DB에서 임의 위치 200곳의 32개 메타데이터 조회를 세 차례 비교했다. 쿼리 실행 계획도 확인했다.

| 방법 | 세 번의 중앙값 | 측정 범위 |
| --- | --- | --- |
| 기존 순번 인덱스 | 3.608 / 2.808 / 1.632ms | SQLite 메타데이터 쿼리만 |
| 글자 수 포함 인덱스 | 0.0103 / 0.0098 / 0.0110ms | 같은 쿼리, covering index |

이 수치를 앱 전체 조회 시간으로 해석하지 않는다. 앱에서는 브리지·본문 읽기·스케줄링 비용이 더해진다. 이미 큰 DB에 인덱스가 없는 경우 최초 생성 비용도 한 번 발생하며, 이번 약 1.2GB 파일에서는 약 2.5초였다.

### Mac은 오래된 위치 이벤트와 실제 행 위치가 문제였다

앞쪽 메시지를 넣거나 제거할 때 실제 행 위치 대신 가상 목록의 추정치를 따라가면 같은 데이터를 반복해서 읽거나 보던 위치가 튀었다. 네이티브 배치가 끝난 다음 위치를 보정하고, 그 이전에 큐에 들어간 오래된 스크롤 이벤트를 구분하도록 수정했다. 미리 읽기도 실제 측정된 첫/마지막 행을 기준으로 한다.

렌더 범위 3화면 후보에서는 일부 구간에서 표시 범위가 모자랐다. 5화면·배치 4개 후보와 최종 실제 휠 실행에서는 본문 전체가 비는 프레임이 없었다. 같은 높이의 행이 이동할 때 위치 통지가 빠지는 경우도 별도로 보정했다.

### iOS는 더 많이 읽는 것으로 해결되지 않았다

읽은 본문을 정리할 때 가상 목록이 스크롤 기준 메시지를 빈 공간으로 바꾸는 문제가 있었다. 의존성의 가상 범위 계산도 수정했지만, iOS의 빠른 관성 스크롤에서는 추가 대응이 필요했다.

| 같은 종류의 짧은 대화·왕복 제스처 | 분석 프레임 | 본문 전체 공백 |
| --- | ---: | ---: |
| 기존 가상 목록, 3화면·16개 읽기 | 2,165 | 22 |
| 더 넓은 가상 목록, 5화면·32개 읽기 | 2,233 | 26 |
| 읽어온 범위의 실제 뷰 유지, 96개 예산 | 2,232 | 0 |

따라서 iOS는 이미 저장소에서 제한된 범위에 또 가상화를 적용하지 않도록 바꿨다. UIKit이 실제 메시지 뷰를 기준으로 위치를 유지한다. 제스처 호출 사이의 관성·대기 시간과 실제 이동 거리는 실행마다 다르므로 이 표로 CPU 절감률을 계산하지 않았다.

Mac·Android·Windows에서 사용하는 가상 목록에는 별도 패치를 넣었다. 이전 첫 메시지가 삭제된 경우 새 첫 메시지의 이전 위치로 표시 범위를 보정하며, 메시지 수가 같은 채 범위만 바뀌는 경우도 처리한다. 설치된 패치의 실제 상태 전환 코드를 회귀 테스트한다.

## 최종 녹화 및 조회 결과

본문을 표시한 뒤 빠르게 왕복 스크롤했다. Mac·iOS 짧은 대화는 네이티브 입력으로, iOS 나머지 길이는 16초 자동 스크롤로 검사했다. Android는 길이별로 36회 빠른 네이티브 스와이프(110ms 동작, 80ms 간격, 중간 방향 반전)를 사용했다. 입력 방식과 실제 이동 거리가 달라 플랫폼 간 속도 순위를 매기는 표는 아니다.

| 환경·대화 | 분석 프레임 | 전체 공백 프레임 | 스크롤 중 본문 조회 | 최대 본문 조회 시간 |
| --- | ---: | ---: | ---: | ---: |
| Mac 짧은 대화, 실제 휠 | 2,713 | 0 | 9회 / 144개 | 24.9ms |
| iOS 짧은 대화, 제스처 | 2,232 | 0 | 41회 / 656개 | 25.6ms |
| iOS 10,000자 | 907 | 0 | 2회 / 2개 | 8.9ms |
| iOS 1,000자 | 905 | 0 | 0회 | 초기 범위로 충족 |
| iOS 혼합 길이 | 892 | 0 | 2회 / 8개 | 14.5ms |
| iOS 50,000자 삽입 | 842 | 0 | 1회 / 1개 | 17.9ms |
| Android 짧은 대화 | 541 | 0 | 10회 / 160개 | 43.9ms |
| Android 10,000자 | 548 | 0 | 1회 / 1개 | 6.3ms |
| Android 1,000자 | 545 | 0 | 0회 | 초기 범위로 충족 |
| Android 혼합 길이 | 552 | 0 | 1회 / 4개 | 7.1ms |
| Android 50,000자 삽입 | 554 | 0 | 1회 / 1개 | 10.0ms |

조회 수에는 초기 진입 전에 읽은 분량이 포함되지 않는다. 1,000자 대화는 초기 32개가 해당 왕복 경로를 감쌌다. 10,000자 메시지는 한 행이 여러 화면을 차지하므로 같은 이동 거리에서 방문하는 메시지 수가 훨씬 적다.

Mac 카드 목록은 16초 동안 12회/288개의 가벼운 목록 행, 채팅방 목록은 5회/120개 행을 추가로 읽었다. 각각 797개·1,169개 분석 프레임에서 전체 목록 공백은 없었다. 카드 본문 1만 개를 함께 읽지 않는다. 다만 카드 이미지에는 기존 샘플 자산을 재사용했으므로, 서로 다른 대용량 이미지 1만 개의 다운로드·디코딩 부하는 이 실험으로 검증하지 않았다.

Mac 짧은 대화의 본문 보관 최대치는 160개/4,400자였고 실제 마운트된 행은 최대 82개였다. Android는 160개/4,400자 중 최대 59개 행이 마운트됐고, 앱 전체 PSS는 약 219.8MiB였다. 방의 모든 본문을 올리지 않는 것과 앱 메모리가 글자 수만큼만 든다는 것은 다르다.

## 지연 원인을 구분한 대조 실험

### 로딩을 일부러 1초 늦췄을 때

같은 Android 짧은 대화·36회 제스처에서 본문 조회에 1초 지연을 넣었다. 정상 실행은 읽은 범위 끝에서 로딩을 기다리는 표본이 0개였고, 지연 실행은 29개였다. 조회 최대값도 43.9ms에서 1,022.2ms로 변했다. 기존 본문은 남아 있어 지연 실행의 492개 분석 프레임에도 전체 공백은 없었지만, 스크롤은 읽은 범위 끝에서 기다렸다.

즉 **빈 프레임 0개만으로 사용자가 기다리지 않았다고 판단하지 않는다.** Mac의 순간적인 2페이지 휠 입력에서도 이런 경계 대기 표본 4개가 있었다. 일반적인 관성 스크롤과 즉시 큰 거리를 이동시키는 입력을 구분해 기록했다.

### Android 프레임 추적과 녹화 유무 비교

Perfetto FrameTimeline, RenderThread, 메인 스레드, 스케줄링 상태를 함께 기록했다. `Prediction Error`, 버퍼 적체, 앱 마감 초과, 합성기 마감 초과를 같은 지표로 합치지 않았다. [Perfetto 공식 FrameTimeline 설명](https://perfetto.dev/docs/data-sources/frametimeline).

녹화 실행의 앱 프레임 569개 중 `App Deadline Missed`가 포함된 프레임은 9개였다. 녹화를 끈 대응 실행에서는 앱 프레임 549개 중 11개였다. 한 쌍으로 통계적 우열을 말할 수는 없지만, **녹화를 끄면 문제가 없어지는 현상은 아니었다.**

긴 렌더 프레임 하나에서 `DrawFrame`은 63.72ms였으나 RenderThread가 CPU에서 실행된 시간은 2.84ms, 수면/대기 상태는 60.49ms였다. 동시에 다른 구간에는 뷰 마운트 작업 25.07ms도 있었다. 따라서 DB 읽기 지연 하나로 설명되지 않으며, 렌더 파이프라인의 대기와 앱의 뷰 작업을 함께 봐야 한다. 이 추적만으로 호스트 GPU·에뮬레이터·실제 기기에서의 비중까지 확정할 수는 없다.

### 긴 텍스트 자체의 비용

50,000자 메시지는 분량 예산보다 커도 하나의 원문으로 표시한다. 이 행을 처음 배치할 때 Mac·iOS의 JS 관측 간격에 약 100ms 수준의 피크가 남았다. Mac의 별도 CPU 샘플에는 React Native 텍스트 배치·CoreText·AppKit 텍스트 그리기 경로가 확인됐다. 샘플과 각 지연 프레임이 완전히 대응된 것은 아니므로 정확한 기여율로 해석하지 않는다.

이번 변경은 과도한 **전체 기록 로드**와 잘못된 스크롤 기준을 해결한다. 극단적으로 긴 단일 메시지를 언제나 한 프레임에 배치한다는 보장은 하지 않는다. 이를 더 줄이려면 메시지 내부 단위의 렌더링까지 따로 검증해야 한다.

## 해석 범위와 검증

- 영상 전체를 프레임별로 디코딩해 본문 전체 공백 후보를 찾고, 대표·실패 구간을 이미지로 직접 확인했다. 밝기 기준 검출은 부분 공백·미세한 떨림·중복 프레임을 모두 증명하는 검사는 아니다.
- JS의 16ms 측정 루프는 **화면 FPS가 아니다**. RN macOS의 bridgeless rAF 구현 때문에 초기 무제한 반복 측정이 왜곡돼 해당 실행은 버리고 제한된 타이머 드라이버로 다시 측정했다.
- 영상 타임스탬프에는 녹화·인코딩·제스처 사이 정지의 영향도 있다. 표시 완료 시간이나 OS 마감 초과를 영상 간격 하나로 대체하지 않았다.
- `firstBodyLayoutMs`는 벤치마크 React 컴포넌트 시작부터 첫 본문 레이아웃까지다. OS 프로세스 시작부터의 콜드 스타트 시간이 아니다. CPU 샘플러를 함께 켠 진입 시간은 일반 실행과 비교하지 않았다.
- 정상 상태의 짧은 반복 실행이며, 실제 휴대폰의 발열·저장장치·저전력 모드·120Hz 및 Windows 네이티브 결과는 남아 있다. 수십만 개 검색이나 서로 다른 이미지 1만 개는 별도 부하다.
- `npm run verify`: 타입 검사, **94개 파일·796개 테스트**, 웹 빌드 통과. SQLite·IndexedDB 저장과 예산 경계, 화면 복원, 오래된 이벤트, 의존성 가상 범위 패치를 검사했다.
- macOS·iOS·Android의 일반 Release 빌드도 다시 성공시켰다. 벤치마크 진입점이 일반 산출물에 남지 않도록 복구했다. iOS는 새 SDK에서 오래된 Pod 타깃이 거부돼 명령에 앱과 같은 `IPHONEOS_DEPLOYMENT_TARGET=15.1`을 지정했다. Windows 빌드는 실행하지 않았다.
